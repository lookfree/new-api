# Zetone · 支付宝与微信支付官方直连设计

日期：2026-09-05
分支：`zetone`
状态：实施中

上游只带了易支付协议、Stripe、Creem、Waffo。易支付里那两个 alipay、wxpay 走的是第三方聚合通道，不是官方直连，合规上有风险，费率也不透明。本次接官方直连。

## 0. 决策记录

征询用户时对方暂时离开，以下按推荐方案推进。

| 议题 | 选定方案 | 说明 |
|---|---|---|
| 产品形态 | 支付宝「电脑网站支付」跳转官方收银台；微信 Native 扫码支付，页内出二维码 | PC 端 SaaS 的标准做法，两家各只需签约一个产品。手机网页支付可后续再加 |
| 无资质时如何验证 | 支付宝用官方沙箱真实跑通；微信没有真沙箱，用单元测试覆盖签名与回调验签 | 微信支付的沙箱环境官方已下线，拿到商户号后再用小额真实交易做最终验证 |
| 依赖 | 不引入 SDK，用标准库自行实现签名与验签 | 保持 fork 的依赖面不变，减少 rebase 与审计负担。两家的签名算法都在标准库能力范围内 |
| 微信证书模式 | 使用微信支付公钥模式，而非平台证书模式 | 公钥模式只需在商户平台下载一次公钥，不需要实现证书下载与轮换。证书轮换是这套协议里最容易出错的一环，能绕开就绕开 |

## 1. 复用已有的结算骨架

上游的充值流程已经很完整，不需要新造：

1. 用户发起充值，创建一条 `pending` 的 `top_ups` 记录，生成商户订单号。
2. 跳转或扫码完成支付。
3. 支付平台回调服务端。
4. 服务端验签，然后走结算函数把额度记到用户头上。

结算入口是 `model/topup.go` 里的 `settleTopUpCredit`，它同时负责加额度和发邀请返利。本次只需为两家各写一个 `Recharge*` 函数，复用同一个入口，返利、幂等、钱包上限这些都自动继承。

新增两个 provider 常量：`alipay` 与 `wechat`。

## 2. 资金安全要求

这是全系统最危险的一段代码，以下每一条都是硬要求。

**回调必须先验签再看内容。** 未通过签名校验的请求一律当作伪造，直接返回失败，不做任何数据库写入。回调地址是公开的，任何人都能构造请求。

**必须核对金额。** 验签通过只能证明请求来自支付平台，不能证明金额正确。必须把回调里的实付金额与订单记录里的应付金额逐笔比对，不一致就拒绝并告警。否则用户可以自行构造一笔一分钱的订单去兑换一百元的额度。

**必须核对商户号与应用号。** 防止别人拿自己的商户号发起回调来给我方用户充值。

**必须幂等。** 支付平台会重复推送回调直到收到成功响应。结算函数已有基于订单状态的幂等保护，两家都必须走它，不能绕过。

**金额换算不得用裸类型转换。** 支付宝以元为单位的字符串、微信以分为单位的整数，都要经 `decimal` 换算后再走 `common.WalletQuotaFromDecimalStrict`，遵守仓库既有的计费安全规范。

**密钥不得出现在日志与接口响应里。** 商户私钥、APIv3 密钥只进配置存储，`GetStatus` 只暴露「是否已启用」这一个布尔值。

## 3. 支付宝

### 配置

应用 ID、应用私钥、支付宝公钥、是否沙箱。沙箱与生产的网关地址不同，由开关切换。

### 下单

调用 `alipay.trade.page.pay`，服务端不发请求，而是生成一个带签名的表单跳转地址，浏览器跳过去就是官方收银台。这是该产品的标准用法，比服务端下单少一次往返。

签名用 RSA2，对排序后的参数做 SHA256withRSA。

### 回调

支付宝以表单方式 POST 异步通知。验签规则：剔除 `sign` 与 `sign_type` 两个字段，其余按键排序拼接，用支付宝公钥验 RSA2 签名。

验签通过后依次核对：应用 ID 是我方、交易状态为成功、商户订单号存在且处于待支付、实付金额与订单一致。全部满足才结算。

处理成功必须返回纯文本 `success`，否则支付宝会持续重推。

## 4. 微信支付

### 配置

商户号、应用 ID、APIv3 密钥、商户证书序列号、商户私钥、微信支付公钥及其 ID。

### 下单

调用 Native 支付下单接口，服务端拿到一个 `code_url`，前端渲染成二维码。请求需带 `Authorization` 头，内容是用商户私钥对「方法、路径、时间戳、随机串、请求体」签名后的结果。

### 回调

微信以 JSON POST 通知，业务数据是加密的。处理分三步：

1. 用微信支付公钥验证回调签名，材料是响应头里的时间戳、随机串与请求体。
2. 用 APIv3 密钥以 AES-256-GCM 解密 `resource` 字段，得到真实的交易数据。
3. 核对商户号、交易状态、订单号与金额，再结算。

时间戳超过五分钟的回调直接拒绝，防重放。

处理结果以 JSON 返回，失败时必须返回非 200，否则微信认为已成功而不再重推。

## 5. 验证记录

### 密码学层

30 个子测试全部通过，覆盖：

- 支付宝待签名串的构造：排序、剔除签名字段、剔除空值、不做 URL 转义。这个串写错是支付宝对接最常见的静默失败。
- 支付宝签名与验签往返，以及三种攻击：篡改金额后沿用原签名、用另一把私钥伪造、签名缺失或非 base64。
- 密钥解析同时接受带 PEM 头和商户后台直接复制的裸 base64，因为运营多半会粘贴后者，此时报错看起来像凭据错误而非格式问题。
- 微信请求与回调的待签名串逐行比对，包括空 body 也必须以换行结尾这一条。
- 微信回调验签，含篡改 body、时间戳过期、时间戳超前、窗口边界内接受、缺失头部、时间戳非数字。
- 微信回调解密，含正确往返、错误的 APIv3 密钥、篡改关联数据、密钥长度错误、随机串长度错误、非 base64 密文。

### 支付宝端到端

用一对测试密钥把「支付宝公钥」设成本地公钥，从而能签出服务端认可的回调，真实跑完整条链路：

| 场景 | 结果 |
|---|---|
| 下单 | 成功，返回带 RSA2 签名的收银台地址，金额按分组倍率算出 730 元 |
| 无签名的伪造回调 | 拒绝 |
| 乱签名的伪造回调 | 拒绝 |
| 验签通过但只付 1 元想换 730 元额度 | 拒绝，并记录订单应付与实付的差异 |
| 正常回调 | 成功入账 |
| 重复回调 | 返回成功但不重复入账，额度与订单状态不变 |

日志逐条记录了拒绝原因和客户端地址。

### 金额核对

9 个子测试锁住比对规则：足额、正负一分以内容差、少付一元、一元换七百三、零元、负数、超额十倍、小数金额。另有一个测试把容差钉死在一分，防止后人放宽它把真实少付放进来。

### 尚未验证

微信支付缺真实商户号，下单与回调只有单元测试覆盖，没有跑过真实网关。拿到资质后必须用一笔小额真实交易补验，这是上线前的硬门槛。

## 6. 上线前提

两家都要求企业资质与已备案域名，回调地址必须是公网可访问的 HTTPS。资质与备案的进度见 P5 部署文档。

在这些到位之前，代码可以写完并通过沙箱与单元测试，但无法产生真实收入。
