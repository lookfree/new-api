分支：`zetone`

原型登录页有三个 Tab：手机号、微信扫码、邮箱，外加 Google 与 GitHub，注册页还有邀请码。P1 换皮、P2 公开页已完成，P3 补齐这条链路。

## 0. 需要提前准备的资质与材料

这部分不写代码也解决不了，建议现在就并行去办。审核期不计入开发工时。

| 登录方式 | 需要什么 | 主体要求 | 大致周期 | 拿到什么 |
|---|---|---|---|---|
| 手机号短信 | 阿里云账号、短信签名报备、短信模板报备、AccessKey | 企业实名认证 | 签名与模板各 1 到 2 个工作日 | AccessKeyId、AccessKeySecret、签名名称、模板 Code |
| 微信扫码 | 微信开放平台「网站应用」 | 企业主体，需 300 元/年认证费，域名须已备案且网站可访问 | 1 到 7 个工作日 | AppID、AppSecret、授权回调域 |
| GitHub | GitHub OAuth App | 无，个人账号即可 | 立即 | Client ID、Client Secret |
| Google | Google Cloud Console 建 OAuth 2.0 客户端 | 无 | 立即 | Client ID、Client Secret、发现地址 |

两条前置依赖：

- **ICP 备案域名**。短信签名报备和微信开放平台都要求域名已备案且站点可正常访问，这是整条链路上最长的一环，先办。
- **企业实名认证**。阿里云短信和微信开放平台都卡这一条。

没有这些材料时系统仍可运行：手机号 Tab 在未配置服务商时不显示，微信、GitHub、Google 各自的开关关闭时按钮也不出现，邮箱注册登录始终可用。

## 1. 手机号短信登录

原型的手机号 Tab 同时出现在登录页和注册页，所以手机号是一等身份，不是仅供绑定的附属字段。

### 数据库

用户表新增 `phone` 列，写法与现有的 `wechat_id`、`telegram_id`、`linux_do_id` 等身份列一致，交给 `AutoMigrate` 处理。

这是 P3 唯一的表结构变更。按仓库规范，必须在 SQLite、MySQL、PostgreSQL 三种数据库上实际验证：全新库建表、由上一版本升级、连续启动两次确认幂等，并确认既有数据与唯一性约束未受影响。验证结果记录在本文档末尾。

### 验证码存储

上游的 `common.RegisterVerificationCodeWithKey` 把验证码存在进程内的内存 Map 里。邮箱验证码量小尚可，但手机号是主登录路径，多节点部署时在 A 节点发码、B 节点校验必然失败。

因此：配置了 Redis 就走 Redis，未配置时回退到上游的内存实现，并在启动日志中提示多节点风险。这样单机部署行为不变，多节点部署才是正确的。

### 短信服务商

做成接口，实现两个：

- `aliyun`：阿里云短信，读取 AccessKey、签名、模板 Code。
- `log`：把验证码写进服务端日志，供本地开发和联调使用。默认就是它，所以没有短信账号也能把注册登录全流程跑通。

服务商与凭据都从后台配置项读取，换服务商不需要改代码。

### 接口

- `POST /api/user/phone/code` 发送验证码。限流复用 `CriticalRateLimit`，叠加人机校验，并按手机号做冷却，防止刷短信。
- `POST /api/user/phone/login` 校验验证码并登录。

登录即注册，与现有微信登录的处理一致：手机号已存在则登录，不存在且后台允许注册则建号。接口接受可选邀请码，对应原型注册页的邀请码字段。

### 边界

- 后台未开启手机号登录，或未配置服务商时，两个接口都直接返回未启用，前端也不渲染该 Tab。
- 手机号格式在服务端校验，前端校验只是为了让用户早点看到问题。
- 验证码错误、过期、超出冷却各自给明确提示，不混为一谈。

## 2. Google 与 GitHub

都不需要写代码。

- GitHub 是上游原生支持，后台填 Client ID 与 Secret 即可。
- Google 走上游的通用 OIDC：发现地址 `https://accounts.google.com/.well-known/openid-configuration`，填入 Client ID 与 Secret，回调地址指向本站。

这部分产出是配置说明，不是代码。

## 6. 三数据库验证记录

日期：2026-09-05。变更内容：`users` 表新增 `phone` 列（字符串，带索引）。

| 数据库 | 版本 | 驱动 |
|---|---|---|
| SQLite | 内置 | glebarez/sqlite，纯 Go |
| MySQL | 8.2.0 | docker `mysql:8.2` |
| PostgreSQL | 15.19 | docker `postgres:15` |

验证方法：先用变更前的二进制（上游 `0ed497f0`）建库并创建一个用户，再用新二进制启动，最后再启动一次。

每种数据库逐项结果，全部通过：

1. 旧版本建出的表确实没有 `phone` 列，升级路径成立。
2. 新版本启动后 `phone` 列被 AutoMigrate 添加。
3. 升级前后用户数不变，既有数据未丢失。
4. 第二次启动日志无重复列、无迁移错误，迁移幂等。
5. 第二次启动后数据仍然完整。

列与索引的实际形态：

- PostgreSQL：`text`，可为空，索引 `idx_users_phone` 已建。
- MySQL：`varchar(191)`，可为空。

复现脚本保存在会话临时目录，核心逻辑是：对每种数据库执行「旧二进制建库并写入数据 → 新二进制启动 → 再启动一次」，并在每一步查询 `information_schema` 确认列存在、查询 `users` 确认行数不变。

### 端到端验证

在 SQLite 实例上走完整流程，均符合预期：

- 未开启时两个接口都返回「管理员未开启手机号登录」。
- 手机号格式错误被拒绝。
- 发送验证码成功，60 秒内重复请求被冷却拦截。
- 错误验证码被拒绝。
- 正确验证码登录成功并自动建号，用户名 `phone_2`，昵称 `138****8000`。
- 同一验证码重放被拒绝，说明用后即失效。
- 第二次登录复用已有账号，用户总数不变，没有重复注册。
- 浏览器端走完整登录，成功进入控制台。

过程中发现并修复了一个日志脱敏缺陷：手机号打码本应是 `138****8000`，实际输出成 `1380013****8000`，多暴露了 4 位，已修并补回归测试。
