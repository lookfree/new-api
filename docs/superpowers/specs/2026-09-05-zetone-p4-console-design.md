# Zetone P4 · 用户端控制台设计

日期：2026-09-05
分支：`zetone`
状态：实施中

原型控制台有七块：概览、模型市场、API 密钥、用量统计、余额与充值、邀请返利、设置。前六块里，模型市场在 P2 已完成，密钥、用量、充值上游功能齐全只差皮肤，真正要新写的是**按充值额比例的邀请返利**。

## 0. 决策记录

征询用户时对方暂时离开，以下按推荐方案推进。两项都可在后台调整，不需要改代码。

| 议题 | 选定方案 | 理由 |
|---|---|---|
| 返利触发时机 | 每次充值都返，比例与开关在后台配置 | 推广动力持续，是多数 API 中转平台的做法。后台可切换为只算首充，所以选错的代价接近零 |
| 返利记录如何存储 | 新建返利流水表 | 每笔返利存下当时的比例与金额，历史记录永远准确、可对账。代价是一次表结构变更，但 P3 已经建好三数据库验证脚本，复用即可 |

## 1. 关键发现

上游全部 7 条充值路径（易支付、Stripe、Creem、Waffo、Waffo Pancake 等）最终都汇聚到 `model/topup.go` 的 `creditTopUpQuota`。因此返利只需挂在这一处附近，所有支付方式自动覆盖，不用逐个改。

兑换码走的是另一条调用链，天然不参与充值返利，与「充值返利」的语义一致。

上游已有且直接可用：邀请码、邀请链接、邀请人数 `aff_count`、待提现额度 `aff_quota`、累计返利 `aff_history_quota`、提现到余额 `TransferAffQuotaToQuota`。钱包页也已经有一张返利卡片。

缺的只有两样：按比例返利的入账逻辑，以及原型那张邀请记录表。

## 2. 返利入账

### 配置

新增一组后台配置，前缀 `affiliate.`：

- `enabled` 总开关，默认关闭。
- `rate` 返利比例，取值 0 到 1，默认 0.1，对应原型的 10%。
- `first_topup_only` 是否只算首次充值，默认关闭。
- `min_topup_quota` 低于该额度的充值不返利，默认 0，用于挡住薅羊毛的碎额充值。

比例在读取时做边界修复：小于 0 或大于 1 一律回落到 0，即等同于不返利，宁可少发也不能发错。

### 计算

返利基数是本次实际入账的额度 `quotaToAdd`，与 `aff_quota` 同单位，避免货币与额度之间来回换算。

计算走 `decimal` 再经 `common.WalletQuotaFromDecimalStrict` 转换，遵守仓库的计费安全规范：不使用裸类型转换，不产生负值，超出钱包上限时报错而不是回绕。计算结果为 0 时直接跳过，不写入空记录。

### 入账位置

在充值结算的同一个事务内完成，与充值成功同生共死：要么充值成功且返利入账，要么两者都回滚。这样不会出现充值成功但返利丢失，也不会出现返利重复入账。

返利加到邀请人的 `aff_quota` 与 `aff_history_quota`，用户在钱包页手动提现到余额，与原型的「提现到余额」一致。

### 边界

- 没有邀请人、邀请人已注销、邀请人就是本人，一律跳过。
- 总开关关闭、比例为 0、低于最低充值额，跳过。
- 只算首充时，查该用户是否已有成功充值记录，有则跳过。
- 返利入账失败不能让充值失败：入账逻辑本身在事务内，但任何非致命错误都记录日志并放行充值，因为用户的钱已经付了。

## 3. 返利流水表

新增 `aff_rewards` 表，字段：邀请人、被邀请人、关联充值单、充值额度、当时的返利比例、返利额度、时间。

按仓库规范，这是本阶段唯一的表结构变更，需在 SQLite、MySQL、PostgreSQL 三库上验证：全新建表、由上一版本升级、连续启动两次确认幂等、既有数据不受影响。验证结果记录在文末。

对邀请人和被邀请人各建索引，列表查询按邀请人过滤。

---

## 4. 邀请返利页

原型的邀请返利页包含：邀请码、邀请链接、返利规则说明、四个统计（累计邀请、已充值人数、累计返利、可提现）、邀请记录表、提现到余额。

上游钱包页已有返利卡片但没有记录表。做法是新增 `/api/user/self/aff/records` 返回当前用户的邀请记录，每行含被邀请人（脱敏）、注册时间、是否充值、累计充值额、我的累计返利。

被邀请人的手机号与邮箱必须脱敏后返回，服务端脱敏，不把完整联系方式发给邀请人。

## 7. 三数据库验证记录

日期：2026-09-05。变更内容：新增 `aff_rewards` 表。

| 数据库 | 版本 |
|---|---|
| SQLite | 内置 glebarez/sqlite，纯 Go |
| MySQL | 8.2.0 |
| PostgreSQL | 15.19 |

方法与 P3 相同：先用变更前的二进制建库并写入数据，再用新二进制启动，最后再启动一次。三种数据库各 5 项、共 15 项全部通过：旧版本确实没有该表、新版本建出该表、既有数据未丢、第二次启动无迁移错误、数据仍完整。

### 端到端验证

在 SQLite 实例上跑通完整返利链路：

- 开启返利并设比例 0.1。
- 用 root 的邀请码通过手机号注册被邀请人，`inviter_id` 正确指向邀请人。
- 造一笔待支付充值单，走管理员补单接口完成结算。
- 被邀请人入账 5000 万额度，邀请人 `aff_quota` 与 `aff_history` 各增加 500 万，正好 10%。
- `aff_rewards` 落一行流水，记录了当时的比例 0.1 与关联充值单号。
- 重复补单同一笔，返回成功但不重复入账，流水仍为一行，说明幂等。
- 邀请记录接口返回被邀请人已脱敏为 `137****7000`，充值额与返利额正确。

过程中修正了一处字段语义错误：邀请记录里的 `topup_quota` 实际装的是充值单位数而非额度，且与原型要展示的「充值额」对不上，已改为 `topup_money` 返回实付金额。
